# AI Diff Review — Спецификация проекта для реализации

## 1. Что мы строим

Desktop-приложение для локального ревью изменений, сделанных AI-агентами (Claude Code, Aider, Cursor CLI, Codex CLI и т.п.) в кодовой базе. Пользователь работает с любым CLI-агентским инструментом как обычно, а это приложение открывается поверх git-репозитория и даёт удобный слой ревью: навигацию по изменённым файлам в правильном порядке, hunk-level Accept/Reject, граф зависимостей между изменёнными файлами, встроенный вызов локального ИИ-агента для объяснения конкретного изменения ("Ask") и автогенерацию комментариев к коду.

Продукт не заменяет агента и не пишет код сам — это ревью-слой поверх локального CLI-агента, который пользователь уже использует.

## 2. Технологический стек

- **Приложение**: Tauri v2 (Rust backend + WebView frontend). Выбран за счёт малого размера бинарника, быстрого старта, низкого потребления RAM и безопасного доступа к файловой системе через Rust-команды.
- **Frontend**: Next.js (App Router, статический экспорт под Tauri) + TypeScript.
- **UI-компоненты**: shadcn/ui + Tailwind CSS. Тема — светлая/тёмная с переключателем (через `next-themes` или аналог, привязка к CSS-переменным shadcn, сохранение выбора темы в локальных настройках приложения).
- **Граф зависимостей**: React Flow (или `@dagrejs/dagre` + кастомный SVG-рендер), стилизация узлов и рёбер — через компоненты shadcn/ui (Card, Badge) для консистентности с остальным интерфейсом.
- **Редактор/diff-view**: Monaco Editor (движок VS Code) в diff-режиме (`IStandaloneDiffEditor`), с decorations (`deltaDecorations`) для кнопок Accept/Reject/Ask/Comment на изменённых строках. Тема Monaco переключается синхронно с общей темой приложения (vs-dark / vs-light).
- **Git-слой**: вызовы системного `git` через Rust `std::process::Command` (не JS git-библиотеки) — надёжнее для больших репозиториев и точечного `git apply`.
- **Анализ зависимостей**: `dependency-cruiser` (Node.js CLI-инструмент), вызывается как подпроцесс из Rust; результат — JSON-граф файлов и их импортов.
- **Хранение состояния/аннотаций**: локальная SQLite база через `tauri-plugin-sql` (либо простой JSON-файл `.reviewstate/` в корне проекта на первом этапе). Настройка темы и путь к CLI-агенту хранятся там же или через `tauri-plugin-store`.
- **Интеграция с ИИ**: только локальный CLI-агент (Claude Code, Aider, Codex CLI и т.п.), без облачных API-ключей на первом этапе. Взаимодействие — через спавн подпроцесса (Rust `std::process::Command` / `tauri-plugin-shell`), передача промпта и контекста через stdin или временный файл, чтение ответа из stdout.
- **Пакетный менеджер**: pnpm.

## 3. Визуальный стиль и UX-принципы

Общий ориентир — VS Code: минималистичный, плотный, но не перегруженный интерфейс, привычный любому разработчику с первого запуска, без обучающих экранов.

- **Минимализм** — никаких декоративных элементов, теней, градиентов или лишней анимации. Только функциональные элементы: текст, иконки, тонкие разделители панелей. Цветовая палитра ограничена нейтральными фонами (тёмно-серый/почти-чёрный для dark, светло-серый/белый для light) плюс 3-4 акцентных цвета для статусов (принято/отклонено/ожидает/неожиданный файл).
- **Плотная, но читаемая раскладка** — как в VS Code: узкие боковые панели с моноширинным или компактным шрифтом для списка файлов, чёткая типографическая иерархия (имя файла крупнее пути, путь — приглушённым серым цветом).
- **Разделители панелей перетаскиваемые** (shadcn `Resizable`) — пользователь сам регулирует ширину левой панели файлов и правой панели графа, как в VS Code Explorer/Sidebar.
- **Иконки вместо текста там, где это очевидно** — Accept/Reject/Ask/Comment на hunk — компактные иконки с тултипом при наведении, а не текстовые кнопки, чтобы не загромождать diff-editor.
- **Статусы через цвет и форму, не только текст** — зелёная полоса слева от hunk = принято, красная = отклонено, серая = не просмотрено, жёлтая точка = есть Ask-ответ или комментарий. Это должно считываться боковым зрением, без чтения текста.
- **Клавиатурные шорткаты как основной способ навигации** — стрелки/`j`/`k` для переключения hunks, `Tab`/`Shift+Tab` для файлов, `A`/`R` для Accept/Reject, `Cmd/Ctrl+K` для быстрого поиска файла — минимизируем количество кликов мышью, аналогично паттерну VS Code Command Palette.
- **Постоянно видимая, но ненавязчивая строка состояния** внизу окна (как status bar в VS Code) — показывает текущий файл, прогресс ревью (N из M файлов просмотрено), статус подключения CLI-агента (иконка "подключен"/"не настроен").
- **Никаких модальных окон для рутинных действий** — Ask и Generate Comment открываются как выдвижная боковая панель (`Sheet`), не блокирующий диалог, чтобы не прерывать поток ревью.
- **Пустые состояния и онбординг — inline, не отдельным туром** — если CLI-агент не настроен, вместо popup-тура показывается ненавязчивая плашка прямо в панели Ask с кнопкой "настроить агента".
- **Согласованная система отступов и радиусов** — использовать Tailwind spacing scale и стандартные radius-токены shadcn без кастомных значений, чтобы интерфейс не "расползался" по мере добавления новых экранов.
- **Тёмная тема — приоритет по умолчанию** (большинство разработчиков открывают редакторы кода в dark mode), светлая — доступна тем же переключателем, что описан в разделе про тему, обе темы должны одинаково хорошо читаться в Monaco editor и в графе зависимостей.

## 4. Подключение локального CLI-агента (флоу)

Отдельный, максимально простой мастер настройки при первом запуске и в настройках:

1. **Автоопределение**: приложение проверяет `PATH` на наличие известных бинарников (`claude`, `aider`, `codex` и т.п.) и предлагает найденные варианты списком с иконкой "обнаружено автоматически".
2. **Ручной ввод**: если агент не найден автоматически — поле для указания пути к исполняемому файлу вручную (с кнопкой "выбрать файл" через системный диалог) плюс поле "команда запуска" (например `claude -p` или `aider --message-file`), так как у разных CLI разный синтаксис вызова с промптом.
3. **Шаблон промпта**: настраиваемый шаблон, как контекст (hunk, файл, связанные файлы) подставляется в аргументы или в stdin конкретного CLI — простой текстовый темплейт с плейсхолдерами (`{{file}}`, `{{hunk}}`, `{{related_files}}`), чтобы не хардкодить формат под каждый инструмент.
4. **Тест-запуск**: кнопка "Проверить подключение" — отправляет тестовый промпт и показывает, пришёл ли ответ и сколько это заняло по времени, чтобы сразу подтвердить, что интеграция работает, до того как пользователь начнёт реальное ревью.
5. **Сохранение профиля агента**: можно сохранить несколько профилей (например, разные CLI для разных проектов) и переключаться между ними в настройках проекта.

Это решает главный риск локальной CLI-интеграции — разнородность интерфейсов разных агентов — через один универсальный адаптер с настраиваемым темплейтом вместо жёстко прописанной интеграции под каждый инструмент.

## 5. Основной пользовательский флоу

1. Пользователь открывает приложение и выбирает папку git-репозитория.
2. Приложение считывает `git diff` (или diff между текущим состоянием и последним коммитом/веткой) и строит список изменённых файлов.
3. Приложение параллельно строит граф зависимостей всего проекта через `dependency-cruiser` и определяет, какие изменённые файлы связаны друг с другом (прямые импорты).
4. Список изменённых файлов сортируется не по алфавиту, а по топологическому порядку графа: сначала файлы-листья (не зависящие от других изменённых файлов), затем файлы, которые их используют — это и есть "порядок чтения".
5. Пользователь переключается между файлами стрелочками (влево/вправо или клавишами), внутри файла — между отдельными hunks (блоками изменений) вторым набором стрелочек.
6. Для каждого hunk доступны действия:
   - **Accept** — применить изменение как есть.
   - **Reject** — откатить конкретный hunk к исходной версии (не весь файл).
   - **Ask** — отправить hunk (+ окружающий контекст файла + связанные по графу файлы) настроенному локальному CLI-агенту с вопросом "почему это изменение было сделано", ответ показывается в боковой панели и сохраняется прикреплённым к этому hunk.
   - **Generate Comment** — тот же вызов агента с другим шаблоном промпта: сгенерировать короткий поясняющий комментарий и вставить его как inline-заметку над функцией/блоком.
7. Пользователь может кликнуть на узел графа зависимостей — это переключает основной вид на diff соответствующего файла.
8. Изменённые, но явно не запрошенные файлы (эвристика: файл не упомянут в тексте задачи/промпта, если он сохранён) помечаются отдельным визуальным флагом как файлы повышенного внимания.
9. Все решения (accept/reject/комментарии/ответы Ask) сохраняются локально и не пропадают при перезапуске приложения.

## 6. Экраны и компоненты интерфейса

### 6.1 Экран выбора проекта
- Выбор папки через системный диалог (Tauri `dialog` plugin).
- Список последних открытых проектов (карточки shadcn `Card`, минималистичные, без лишних иллюстраций).
- Мастер подключения локального CLI-агента (см. раздел 4), доступен также из настроек в любой момент.

### 6.2 Главный экран ревью
Разделён на три зоны, верстка на Next.js + shadcn `ResizablePanel`/`Sheet`, в духе VS Code layout (Activity Bar + Sidebar + Editor + Panel):

- **Левая панель — список файлов**: изменённые файлы в топологическом порядке, с индикатором количества hunks (shadcn `Badge`), статусом (не просмотрен / частично принят / полностью принят / отклонён), флагом "неожиданный файл" (выделение цветом/иконкой). Компактные строки, как в VS Code Explorer.
- **Центральная зона — Monaco diff-editor**: side-by-side или inline (переключаемо через shadcn `Tabs` или `Toggle`), с навигацией по hunks, иконками-кнопками Accept/Reject/Ask/Comment, привязанными к каждому hunk через decorations/content widgets.
- **Правая панель (выдвижная, shadcn `Sheet`)** — граф зависимостей (React Flow), где изменённые файлы подсвечены, связи между ними — рёбра, клик по узлу переключает центральную зону.
- **Нижняя строка состояния** — текущий файл, прогресс ревью, статус CLI-агента (см. раздел 3).

**Переключатель темы** — в верхней панели (header) приложения, иконка солнце/луна (shadcn `DropdownMenu` или простой `Switch`), переключает CSS-класс `dark`/`light` на уровне всего приложения и синхронизирует тему Monaco editor.

### 6.3 Панель Ask / комментариев
- При нажатии Ask — боковая выдвижная панель (shadcn `Sheet`) с полем ввода (можно уточнить вопрос) и ответом агента, который стримится по мере генерации (потоковый вывод из stdout подпроцесса). Не блокирует остальной интерфейс.
- История Ask-диалогов и сгенерированных комментариев сохраняется и привязывается к конкретной строке/hunk навсегда, доступна повторно при возврате к файлу.

### 6.4 Настройки
- Управление профилями локальных CLI-агентов (добавление/редактирование/тест-запуск, см. раздел 4).
- Переключатель темы (дублируется здесь же, как альтернативный доступ).
- Настройка источника diff (сравнение с last commit, с конкретной веткой, или unstaged changes).
- Игнор-паттерны файлов (аналог `.gitignore`) для исключения из ревью (например, lock-файлы, сгенерированный код).
- Настройка клавиатурных шорткатов (просмотр и переопределение, аналогично VS Code Keyboard Shortcuts).

## 7. Ключевые технические модули (для реализации по отдельности)

1. **Git diff parser** — модуль на Rust, вызывает `git diff --numstat` для списка файлов и `git diff -U3` (или больше контекста) для точных hunks с номерами строк. Парсит unified diff формат в структуру: файл → список hunks → строки (added/removed/context) с номерами строк до/после.
2. **Hunk apply/revert engine** — применение или откат конкретного hunk через генерацию мини-патча и `git apply` (с флагом `--reverse` для отклонения), либо через прямую манипуляцию содержимого файла по номерам строк как fallback, если `git apply` не срабатывает на частичный патч.
3. **Dependency graph builder** — обёртка над `dependency-cruiser`, запуск как subprocess с JSON-output, кэширование результата (инвалидация по времени изменения файлов), фильтрация графа до подмножества "изменённые файлы + их прямые соседи (1 hop)".
4. **Topological sort для порядка файлов** — простой алгоритм сортировки списка изменённых файлов по графу зависимостей (файлы без исходящих зависимостей на другие изменённые файлы — первыми).
5. **Local CLI agent adapter** — единый интерфейс `askAgent(context) => AsyncIterator<string>` (потоковый ответ), реализация через спавн подпроцесса (`tauri-plugin-shell`), подстановку контекста в настраиваемый темплейт команды/промпта (см. раздел 4), парсинг stdout построчно для стриминга в UI. Контекст на вход: сам hunk, полный текст файла, список связанных файлов из графа (опционально их содержимое), исходный текст задачи/промпта пользователя (если пользователь его сохранил).
6. **State persistence layer** — SQLite или JSON-хранилище для статусов hunks (accepted/rejected/pending), сохранённых Ask-ответов и сгенерированных комментариев, привязанных к идентификатору файла + hash хunk-а (чтобы не терять привязку при небольших сдвигах строк), а также настроек темы и профилей агентов.
7. **UI: Monaco diff integration** — встраивание Monaco в Next.js-компонент (динамический импорт без SSR, `next/dynamic`), кастомные decorations для рендера кнопок на изменённых строках, обработка событий кликов на decorations, синхронизация темы редактора (`vs-dark`/`light`) с глобальной темой приложения.
8. **UI: граф зависимостей** — React Flow компонент, авто-layout через `dagre`, стилизация узлов по статусу (изменён/не изменён/неожиданный) с использованием токенов темы shadcn/Tailwind, чтобы граф тоже корректно выглядел в обеих темах.
9. **Theme system** — глобальный провайдер темы (light/dark) на уровне Next.js root layout, синхронизация с системной темой ОС по умолчанию при первом запуске, сохранение выбора пользователя в state persistence layer.
10. **Keyboard shortcut manager** — централизованный реестр горячих клавиш (навигация по файлам/hunks, Accept/Reject, поиск файла), с возможностью просмотра и переопределения в настройках.

## 8. MVP — минимальный набор для первого релиза

Приоритет реализации (в этом порядке):

1. Открытие проекта, чтение git diff, список файлов (пока в простом порядке, без графа).
2. Базовый UI-каркас на Next.js + shadcn/ui с рабочим переключением темы (light/dark) и минималистичной VS Code-подобной раскладкой (Sidebar + Editor + Status Bar) — делается рано, так как затрагивает все последующие компоненты.
3. Monaco diff-editor с навигацией по файлам и hunks стрелочками/клавишами, тема синхронизирована с общей.
4. Accept/Reject на уровне hunk с реальным применением к файлам на диске, статус-индикация цветом.
5. Мастер подключения локального CLI-агента (автоопределение + ручной ввод + тест-запуск) и кнопка Ask на hunk.
6. Generate Comment (тот же агент, другой шаблон промпта).
7. Сортировка файлов по топологии графа зависимостей (базовая интеграция dependency-cruiser).
8. Визуализация графа как отдельная панель с подсветкой изменённых файлов.
9. Флаг "неожиданный файл" (сначала можно вручную — пользователь вводит список файлов, которые ожидал изменить, остальные подсвечиваются).

Редактирование кода прямо в diff-editor перед Accept, поддержка нескольких CLI-агентов одновременно с автоматическим выбором по типу задачи, экспорт отчёта о ревью, кастомизация горячих клавиш — за пределами MVP, реализовать после стабилизации базового флоу.

## 9. Нефункциональные требования

- Приложение работает полностью локально; поскольку ИИ-интеграция — только локальный CLI-агент, никакие данные о коде не уходят на внешние серверы через сам продукт (весь трафик, если он есть, контролируется самим CLI-агентом пользователя).
- Все операции с git должны быть безопасны: перед применением/откатом hunk — предупреждение, если в файле есть несохранённые изменения вне git (untracked modifications).
- Поддержка репозиториев любого размера — граф зависимостей должен строиться асинхронно и не блокировать UI, с индикатором прогресса.
- Кроссплатформенность — Windows/macOS/Linux (стандартная цель Tauri).
- Тема приложения должна применяться мгновенно без перезагрузки окна и сохраняться между запусками.
- Интерфейс должен оставаться отзывчивым (без лагов при вводе/скролле) даже на репозиториях с сотнями изменённых файлов — виртуализация списков (`react-virtual` или аналог) для длинных списков файлов и hunks.
